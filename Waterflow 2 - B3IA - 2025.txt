 
Waterflow 2  
 
« Tous les modèles sont faux, mais certains sont utiles. » – George E. P. Box 
 
 
Contexte pédagogique
 
Le projet Waterflow 2 s’inscrit dans la continuité du projet Waterflow, où les 
étudiant·es ont entraîné et déployé un modèle de classification de la 
potabilité de l’eau en s’appuyant sur MLflow, une API Flask et une batterie de 
tests avec PyTest.  
Il s’agit désormais de passer d’un prototype fonctionnel à une application API 
unique plus proche d’un contexte professionnel : exposer et stocker les 
données de prélèvements, automatiser les tests et la livraison, intégrer un 
service d’OCR, et mettre en place un monitoring simple adapté à un contexte 
MLOps. 
 
 
 
 
_1 
 
Rappel du projet Waterflow 
 
Dans Waterflow, vous avez : 
●​ Réalisé une veille sur les pratiques MLOps et sur l’outil MLflow. 
●​ Préparé les données de qualité de l’eau,  
●​ Entraîné un modèle de classification (classique ou réseau de 
neurones), 
●​ Évalué ses performances.​ 
●​ Mis en place un serveur MLflow,  
●​ Suivi les expériences d'entraînement,  
●​ Déployé le modèle dans une API Flask  
●​ Implémenté des tests (unitaires, fonctionnels, non‑régression) avec 
PyTest,  
●​ géré le projet de manière collaborative avec un dépôt GitHub structuré 
(notebook, experiment.py, app.py, environnement de tests, README).​ 
 
Waterflow 2 reprend ce socle pour le prolonger vers la mise à disposition des 
données, la livraison continue et le monitoring, ainsi que la mise en œuvre 
d’une sécurisation by design des données personnelles conforme au RGPD. 
 
Dans Waterflow 2, vous ne redéveloppez pas un micro‑système complet de 
services indépendants, mais vous enrichissez votre projet existant avec une 
API structurée en modules (données, prédiction, OCR) partageant une même 
base de code et une même base de données.

de prédiction permettant de classifier la qualité de l’eau à partir de mesures

●​ Les clients ou agents de terrain de la collectivité territoriale souhaitent 
éviter de saisir manuellement les fiches de laboratoire : ils veulent

_3 
 
Votre mission est de concevoir et développer Waterflow 2, une plateforme 
MLOps industrialisée connectant : 
●​ une API principale structurée offrant des routes de données, de 
prédiction et d’ingestion OCR 
○​ une API de données multi-profils ; 
○​ une API de prédiction basée sur le modèle Waterflow ; 
○​ une API d’ingestion connectée à OCR.space (après veille 
comparative de solutions équivalentes) pour transformer des 
fiches PDF/images en données structurées ; 
●​ une base de données relationnelle conforme au RGPD ; 
●​ une interface web simple pour les experts ; 
●​ un mécanisme de logs et quelques métriques exposées pour le 
monitoring. 
●​ [optionnel] une interface frontend de monitoring 
Vous veillerez à ce que l’application soit conteneurisée, déployable avec des 
tests automatisés et une CI/CD minimale. 
 
Profils utilisateur et authentification simplifiée 
Modèle d’authentification 
Pour simplifier le projet, l’authentification se fait exclusivement par clé API côté 
clients : 
●​ Chaque client de la collectivité possède un compte client contenant : 
●​ un identifiant client (ID client), 
●​ une dénomination (nom de la structure), 
●​ une adresse postale, 
●​ une clé API générée par la plateforme. 
_4 
 
●​ Les administrateurs de la plateforme (analystes qualité / responsable 
d’exploitation ou rôle dédié) sont les seuls à pouvoir : 
●​ créer un compte client avec ID, nom et adresse ; 
●​ générer et régénérer une clé API associée. 
●​ Les clients utilisent uniquement leur clé API pour : 
●​ appeler l’API d’ingestion de prélèvements, 
●​ appeler l’API d’ingestion par OCR (fiches labo), 
●​ consulter leurs données  
●​ consulter les résultats d’analyse du modèle de la plateforme. 
 
Les accès experts (analystes, responsable d’exploitation) peuvent rester dans 
un modèle simple (par exemple un login technique unique configuré côté 
serveur, ou une “auth” très légère) : le cœur du projet se concentre sur la 
sécurité et la séparation des périmètres via clé API client + rôles serveur plutôt 
que sur un système d’authentification complet. Une gestion détaillée des 
droits par utilisateur expert n’est pas attendue 
Profils à prendre en compte 
●​ Client final de la collectivité 
●​ Possède un ID client et une clé API. 
●​ Peut déposer des prélèvements (données structurées ou fiche 
labo PDF/image) et consulter ses propres données et résultats via 
API et/ou une vue simplifiée.  
●​ Analyste qualité 
●​ Accède à tous les prélèvements, dashboards, prédictions, 
données enrichies. 
●​ Suit la cohérence des données et les performances du modèle.

●​ Supervise la santé globale de la plateforme : disponibilité, 
volumes, erreurs, alertes. 
●​ Suit la gestion des clés API, les journaux d’accès et les incidents 
techniques.

Travail demandé 
 
Les étudiant·es repartent obligatoirement de leur projet Waterflow : même 
dépôt GitHub (ou fork), même modèle de base et même architecture 
générale, qu’il s’agit d’enrichir et de durcir.  
Vous devez concevoir et implémenter Waterflow 2 en suivant les étapes 
suivantes : 
1.​ Analyse du besoin et spécifications  
●​ Formaliser le contexte métier et les profils utilisateurs. 
●​ Rédiger les spécifications fonctionnelles (user stories, critères 
d’acceptation) pour client, agent, analyste, responsable. 
●​ Proposer une architecture technique : 
_8 
 
●​ API (une seule API peut porter Data + Model + OCR, plutôt 
que 3 APIs séparées)  
●​ API Data (prélèvements), 
●​ API Model (prédiction Waterflow existante), 
●​ API OCR (ingestion de fiches labo), 
●​ base de données, 
●​ logs de monitoring, 
●​ mécanismes de test 
●​ CI/CD, 
●​ intégration avec OCR.space. 
2.​ Modélisation et base de données 
●​ Concevoir un MCD/MPD incluant au minimum : 
●​ clients (ID client, dénomination, adresse, clé API…), 
●​ prélèvements (date, lieu, mesures, ID client, provenance : 
“Saisie” / “OCR”), 
●​ journaux d’accès et de traitements (pour la traçabilité 
RGPD), 
●​ [si nécessaire] éventuelles tables de support (types de 
mesures, statuts…). 
●​ Implémenter la base SQL (PostgreSQL / MariaDB…) et les scripts 
de création. 
●​ Programmer des scripts d’import/agrégation cohérents avec 
le modèle. Au moins un script attendu. 
3.​ API Data et modèle d’authentification par clé API 
●​ Implémenter une API REST Data exposant au moins : 
_9 
 
●​ POST /api/clients (réservé aux administrateurs) : création 
d’un client avec ID, nom, adresse et génération de la clé 
API. 
●​ GET /api/clients (admin) : liste ou détail des clients. 
●​ POST /api/measurements (client + clé API) : dépôt de 
mesures structurées pour créer un prélèvement. 
●​ GET /api/measurements (client + clé API) : liste des 
prélèvements du client (filtrage par clé API). 
●​ GET /api/measurements/admin (expert) : vue globale 
filtrable. 
●​ Gérer la validation des requêtes (schémas, types, formats) et 
le contrôle d’accès par clé API. 
●​ Documenter cette API (OpenAPI / Swagger) afin de la rendre 
intégrable par des systèmes externes. 
4.​ API Model 
●​ Réutiliser ou adapter le modèle et l’API de prédiction du projet 
Waterflow (Flask ou FastAPI) en l’intégrant dans la nouvelle 
architecture. 
●​ Exposer une route, par exemple POST /api/predict, prenant en 
entrée un prélèvement (ou un ID de prélèvement) et renvoyant 
la prédiction + métadonnées (version de modèle, scores). 
●​ Assurer au minimum le suivi des versions,des expériences et 
quelques métriques via MLflow (monitoring modèle). Un suivi 
exhaustif des expériences est optionnel. 
●​ Écrire des tests unitaires et d’intégration (2 ou 3) pour valider le 
pipeline de prédiction. 
5.​ API OCR avec OCR.space 
_10 
 
●​ Après une veille comparative sur des services d’IA équivalents 
répondant aux besoins de l’application, intégrer l’API 
OCR.space (https://api.ocr.space/parse/image) ou un autre 
service équivalent, pour traiter des fichiers image/PDF de 
fiches de laboratoire. 
●​ Concevoir une route, par exemple : 
●​ POST /api/ocr/lab-report (client + clé API) : 
●​ reçoit un fichier (image/PDF) représentant une 
fiche laboratoire ; 
●​ appelle OCR.space (via file ou base64Image) avec la 
clé API OCR de la plateforme ; 
●​ parse la réponse JSON pour extraire les champs 
utiles (date, ID client, mesures physico-chimiques, 
etc.) ; 
●​ crée un prélèvement structuré identique à celui de 
POST /api/measurements (ou utilise la même logique 
métier) ; 
●​ renvoie au client un identifiant de prélèvement et 
les données extraites. 
●​ Documenter cette route et les erreurs possibles (timeout OCR, 
fichier illisible, champs manquants). 
6.​ Interface web expert 
●​ Développer une interface simple (Dash, Streamlit ou frontend 
classique;  Streamlit fortement recommandé pour limiter la 
complexité front) pour : 
●​ consulter tous les prélèvements, 
_11 
 
●​ filtrer par client, provenance (Saisie / OCR), date, résultat 
modèle, 
●​ [option] afficher quelques indicateurs clés (nombre de 
prélèvements, répartition potables / non potables, etc.), 
●​ [option] visualiser quelques journaux d’accès (dans une 
vue d’administration). 
7.​ Tests, CI/CD, monitoring et incidents 
●​ Écrire des tests unitaires et d’intégration (PyTest…) pour : 
●​ API Data, API Model, API OCR, validation des schémas de 
données, 
●​ au moins un test de bout en bout (dépôt de fiche labo → 
OCR → prélèvement structuré → prédiction modèle). 
●​ Mettre en place une CI simple (GitHub Actions, GitLab CI) 
exécutant les tests à chaque push/PR. 
●​ Conteneuriser l’application (Docker) pour faciliter le 
déploiement et la reproductibilité. 
●​ Mettre en place un mécanisme de monitoring applicatif : 
●​ journalisation des requêtes (client, route, status, durée), 
●​ quelques métriques (nombre de requêtes OCR, taux 
d’erreur, temps moyen de traitement). 
●​ [Optionnel] ajouter une interface Prometheus + Grafana 
pour visualiser les journaux, logs et indicateurs ou 
métriques  
●​ Mettre en place une intégration continue minimale (GitHub 
Actions, GitLab CI…) qui installe les dépendances et exécute la 
_12 
 
suite de tests à chaque push. La livraison continue (build et 
déploiement automatique) est un bonus si elle est réalisée. 
●​ Prévoir au moins un scénario d’incident (par exemple, service 
OCR indisponible, clé API OCR invalide, fail d’import) et 
documenter : 
●​ la détection de l’incident (logs, métriques), 
●​ le diagnostic, 
●​ la correction et sa vérification, 
●​ la mise à jour du code / de la configuration et son 
versionnement. 
Dimensions RGPD et gouvernance des accès 
L’introduction de l’ID client + clé API permet de traiter des enjeux RGPD 
concrets, en base de données et dans les logs : 
●​ séparation stricte des périmètres : un client ne voit que ses données ; 
●​ minimisation des données personnelles stockées (ID technique + 
adresse) ; 
●​ journalisation des accès par clé API pour pouvoir répondre à un audit 
de sécurité ; 
●​ documentation des durées et règles de conservation des données 
(prélèvements, logs). 
Les étudiant·es devront : 
●​ expliciter, dans la documentation, quelles données sont considérées 
comme personnelles ; 
●​ décrire comment les journaux d’accès sont gérés, à quelles fins et 
pour combien de temps ; 
_13 
 
●​ expliquer comment la génération et la régénération des clés API sont 
gérées (régénération en cas de compromission). Au minimum, la 
documentation doit expliquer comment un client ne peut accéder 
qu’à ses données (clé API + filtres) et comment une clé compromise 
pourrait être régénérée.

●​ Les scripts d’initialisation de la base de données et d’import de jeux

●​ Les fichiers de configuration nécessaires à l’exécution (configuration

2. Conteneurisation et exécution
